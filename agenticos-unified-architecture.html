Product Thesis

AgenticOS is a local-first AI operating system for work. It combines model providers, terminal-native coding agents, vault memory, real metrics, social research, routines, approvals, MCP tools, and startup operations into a single cockpit. The two older HTML documents describe complementary halves: AgenticOS as the broad AI OS, and the Obsidian command center as the vault-native daily operating layer. This unified document describes the merged product.

What AgenticOS Is

A control plane that receives goals, routes them to skills, selects a provider, loads vault and project context, executes a workflow, records every tool action, writes markdown artifacts, indexes memory, and displays live run economics. It is not just a chat UI. It is an operational shell around agentic workflows.

What the Obsidian Layer Adds

A durable, human-readable memory substrate: daily notes, raw capture, curated wiki pages, project context, output artifacts, backlinks, graph indexing, promotion candidates, conflict detection, and pattern detection. The vault gives the AI system continuity without hiding data in a proprietary black box.

04

Core Flow

The central loop converts natural language into governed work. Every run becomes a persisted object with plan, steps, tool calls, approvals, artifacts, token usage, and cost. This is the difference between a chat wrapper and a real AI operating system.

1. Prompt

User types a task, selects a skill, or opens a prefilled template from the skill grid.

2. Route

The engine classifies the goal, picks skill category, risk level, mode, and expected tool surface.

3. Context

Project markdown, memory index, and recent vault notes are loaded into a bounded prompt window.

4. Execute

Provider call, CLI call, swarm run, or adapter call is executed with approval gates where required.

5. Persist

Artifacts are written to the vault, runs are stored in SQLite, and memory is indexed.

Planning

Agent Plan

Each run creates plan steps: receive and classify goal, load memory, execute workflow, save artifacts and memory. Risk and approval requirements are computed before actions proceed.

Execution

Tool Calls

Tool calls record tool name, action, input JSON, output, risk level, status, and timestamp. This gives auditability even when the action is a dry-run observation.

Artifacts

Vault Output

Final output is saved as markdown under the target skill folder. Frontmatter captures tags, category, skill, source, runId, cost, and selected model.

PromptConsole
  -> POST /api/runs
    -> startRun()
      -> buildAndPersistRun()
      -> executeWorkflow()
        -> listMemoryItems()
        -> loadVaultContext()
        -> generateFinalOutput()
          -> generateWithModel() or runSwarm()
        -> writeVaultMarkdown()
        -> indexGeneratedArtifact()
        -> updateRun()

06

Vault and Memory Architecture

The vault is the shared memory medium between human and AI. It must be readable, portable, editable, and graphable. AgenticOS uses the filesystem for markdown artifacts and SQLite for indexes, graph metadata, run state, and search acceleration.

Vault Folder Model

The vault can be opened directly in Obsidian. Agent outputs are markdown files, not opaque database blobs.

vault/
  daily/        daily notes, plans, reviews
  runs/         generic run artifacts
  content/      drafts, scripts, posts, cascades
  projects/     project snapshots and reusable context
  raw/          captured notes and inbox items
  wiki/         promoted durable knowledge

Memory Index

The local DB tracks memory entries, vault nodes, links, backlinks, word counts, file existence, and timestamps.

memory_index:
  id, file_path, title, type, tags_json,
  summary, last_updated, embedding_placeholder,
  importance_score

vault_nodes:
  path, title, folder, word_count,
  link_count, backlink_count, last_indexed

vault_links:
  source, target, resolved_path, created_at

Capture

Raw notes, prompt outputs, daily logs, and generated artifacts enter the vault as markdown.

Promote

Promotion candidates can be identified from raw notes with backlink thresholds and moved into curated wiki/project areas.

Connect

Wiki links are extracted, outlinks/backlinks are indexed, and graph stats expose orphan and most-linked notes.

Conflict

Conflict detection modules can identify duplicate or competing vault material for cleanup.

Patterns

Pattern detection scans recent windows to surface repeated themes, repeated files, and knowledge signals.

Context Window

Workflow generation pulls bounded vault snapshots by time window, max files, per-file chars, and total chars.

Terminal Runtime

The terminal is a first-class app feature, not a text box. It starts real local processes and streams output to xterm.js through server-sent events. Installed CLIs are discovered and missing CLIs show actionable install hints.

Backend

  • PTY process manager in lib/terminal/manager.ts.
  • Adapters in lib/terminal/adapters.ts.
  • Availability checks through command discovery.
  • Windows PTY launches CLI shims through cmd.exe /d /s /c.
  • Session history replay for late subscribers.
  • Resize support, raw input, line input, kill, and session listing.

Frontend

  • xterm.js viewport with fit addon.
  • SSE stream decodes base64 chunks to preserve ANSI output.
  • Provider selector uses backend adapter statuses.
  • Active model provider can influence default terminal choice.
  • Unavailable adapters stay visible with install guidance.
POST /api/terminal/sessions        create session
GET  /api/terminal/sessions        list sessions and adapter availability
GET  /api/terminal/:id             session metadata
GET  /api/terminal/:id/stream      server-sent output stream
POST /api/terminal/:id/input       raw keystrokes or line input
DELETE /api/terminal/:id           kill session

Permissions and Safety

Safety is part of the architecture, not a UI checkbox. The system distinguishes read-only work, drafts, approvals, auto-execution, and disabled capabilities. Risk is inferred from action language and skill metadata.

Read-only

Safe reads from vault, GitHub, HN, YouTube stats, model catalogs, metrics, and local DB.

low risk

Draft-only

Generate email drafts, captions, code suggestions, schedules, documents, and plans without sending or mutating systems.

review

Approval Required

Sending email, pushing branches, modifying files outside policy, refunds, product updates, customer changes, publishing.

high risk

To launch as a startup product, the local-first prototype needs credentials, OAuth apps, hosted infrastructure, observability, and billing controls. The repo includes .env.example and STARTUP_WIRING.md as the operational checklist.

Production Requirements

  • Managed database instead of local SQL.js for multi-user deployments.
  • Secrets manager instead of plaintext environment files.
  • OAuth apps for Google, Meta/Instagram, TikTok, Shopify, and GitHub.
  • Background worker for routines and scheduled jobs.
  • Auth, tenant isolation, rate limits, usage caps, and billing enforcement.
  • Audit logs, backups, data deletion, privacy policy, and terms.

Roadmap

The next milestones are about turning the local-first product into a dependable startup-grade system while preserving the vault-native advantage.

Phase 1
Stabilize local product.

Keep terminal PTY reliable, finish settings feedback, verify provider runs, harden run streaming, and add adapter-level tests.

Phase 2
Wire live read adapters.

Complete GitHub, Google, Firecrawl, YouTube, Instagram, TikTok, Stripe, Shopify, and CRM read paths with real credentials.

Phase 3
Harden approval-gated writes.

Implement drafts first, require approvals for writes, log exact payloads, and add rollback guidance for external mutations.

Phase 4
Production infrastructure.

Add auth, hosted database, queue worker, secret vault, telemetry, billing, org/workspace boundaries, backups, and deployment pipeline.

Phase 5
Moat expansion.

Vault graph UX, semantic memory, reusable agent packs, marketplace skills, local voice mode, mobile capture, and team knowledge workflows.

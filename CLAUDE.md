# AgenticOS Agent Guide

This file is the primary project map for Claude Code and other coding agents working in this repository. It is intentionally detailed so a fresh LLM can understand the app from zero context, make narrow edits, and predict downstream effects before changing code.

AgenticOS is a local-first AI workflow operating layer built with Next.js App Router, React, TypeScript, SQL.js, local markdown vault storage, model-provider adapters, CLI terminal sessions, seeded skills, routines, approvals, and command-center dashboards.

## Non-Negotiable Operating Rules

- Local-first by default. Runtime data lives under `vault/` and `.agenticos/agenticos.sqlite`.
- Risky actions stay approval-gated. Never send, delete, publish, charge, refund, push, install, mutate production/customer data, expose secrets, or write to external systems without explicit user approval.
- The markdown vault is durable memory. Store only user-provided content and artifacts generated by runs.
- Do not treat mock adapters as real external integrations. Many integrations are intentionally mock-first unless credentials exist.
- Preserve user files and runtime data. Do not delete `vault/`, `.agenticos/`, `.env.local`, or generated sqlite data unless explicitly requested.
- Prefer surgical edits. Most features are connected through a few central modules; changing one shared function often affects multiple pages and API routes.

## Runtime Configuration

All core paths and runtime defaults come from `agenticos.config.ts`.

- `projectContextPath`: defaults to `.agenticos-project`; markdown here is loaded into model prompts by `lib/agent/project-context.ts`.
- `vaultPath`: defaults to `vault`; used by `lib/vault/service.ts`, terminal sessions, command-center tasks, and generated artifacts.
- `databasePath`: defaults to `.agenticos/agenticos.sqlite`; used by `lib/db/client.ts`.
- `mode`: `AGENTICOS_MODE` or `mock`.
- `defaultProvider`: `AGENTICOS_PROVIDER` or `claude-code`.
- `budgets`: five-hour token cap, weekly minutes, daily routines; consumed by `lib/mock/metrics.ts`.
- `allowedCommandRoots`: currently `[process.cwd()]`; policy intent for command safety.
- Social/env keys: YouTube, Instagram, TikTok, and provider API keys.

Important environment variables:

- Provider APIs: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `NVIDIA_API_KEY`, `OPENROUTER_API_KEY`, `GEMINI_API_KEY`, `GROK_API_KEY` or `XAI_API_KEY`.
- CLI overrides: `CLAUDE_CLI_PATH`, `CODEX_CLI_PATH`, `GEMINI_CLI_PATH`, `COPILOT_CLI_PATH`, `OLLAMA_CLI_PATH`, `AIDER_CLI_PATH`, `AMP_CLI_PATH`.
- Local model: `OLLAMA_MODEL`.
- Integrations: `GITHUB_TOKEN`, Google OAuth env vars, `STRIPE_SECRET_KEY`, Shopify env vars, CRM env vars, `FIRECRAWL_API_KEY`, YouTube/Instagram/TikTok env vars.

## Core Data Flows

### 1. Application Startup

1. `app/layout.tsx` imports global CSS and wraps every route in `AppShell` and `CommandPalette`.
2. At module load, `app/layout.tsx` calls `startScheduler()` from `lib/scheduler/worker.ts` and `indexVaultGraph()` from `lib/vault/graph.ts` in fire-and-forget mode.
3. `startScheduler()` loads routines from SQL.js through `listRoutines()` and registers cron tasks.
4. `indexVaultGraph()` scans markdown in `vault/`, extracts wiki links, and persists graph rows through `batchUpsertVaultGraph()`.
5. `AppShell` renders persistent navigation; all page content is inserted inside the shell.

Change impact:

- Changing `app/layout.tsx` affects every route and can trigger server-side side effects on app startup.
- Changing scheduler startup or graph indexing can slow every server boot or page render if made blocking.
- Changing `AppShell` affects navigation, top-level branding, and every app page.

### 2. Prompt Console to Completed Run

1. User opens `/dashboard`.
2. `app/dashboard/page.tsx` loads runs, integrations, recent vault files, skills, and model providers.
3. `components/dashboard/prompt-console.tsx` renders skills and a prompt textarea.
4. When the user clicks Run, the client reads selected provider/model/thinking/effort from `localStorage`.
5. The client posts to `POST /api/runs` with `{ prompt, skillId, dryRun: true, modelProfile }`.
6. `app/api/runs/route.ts` validates with Zod and calls `startRun()` from `lib/agent/engine.ts`.
7. `startRun()` creates a persisted run immediately, launches `executeWorkflow()` in the background, and returns the run id.
8. The client navigates to `/runs/[id]`.
9. `app/runs/[id]/page.tsx` loads the run and plan from repositories. If status is not terminal, it mounts `RunPoller`.
10. `components/runs/run-poller.tsx` subscribes to `GET /api/runs/[id]/stream`.
11. The stream route polls `getRun(id)` every 500ms and sends SSE status, step, final, error, or timeout events.
12. When final status arrives, `RunPoller` refreshes the page so the final output and artifacts appear.

Core engine details:

- `buildAndPersistRun()` creates run metadata and an `AgentPlan`.
- `buildPlan()` derives category, risk, execution mode, tool names, and approval requirements.
- `runWorkflowSteps()` logs each planned step, creates a tool call, blocks for approval if needed, then generates final output.
- `generateFinalOutput()` chooses fallback mock output, single-provider generation, or `runSwarm()` based on request and skill.
- `writeVaultMarkdown()` writes the generated artifact into the skill output folder.
- `indexGeneratedArtifact()` inserts/updates the memory index row for the generated file.
- `updateRun()` finalizes status, tokens, cost, files, errors, final output, and artifacts.

Change impact:

- Changing `types/run.ts`, `types/agent.ts`, or DB schema in `lib/db/client.ts` requires updates to repository mapping and every page/API that displays runs.
- Changing `startRun()` vs `createAndRunWorkflow()` changes HTTP timeout behavior. `startRun()` returns before model generation; `createAndRunWorkflow()` blocks until completion.
- Changing `buildPlan()` affects approvals, tool call logs, plan previews, and risk display.
- Changing `generateFinalOutput()` affects all run outputs, cost estimates, model errors, and swarm behavior.
- Changing `writeVaultMarkdown()` changes every generated artifact path and frontmatter format.

### 3. Model Provider Selection and Generation

1. `/settings` renders `ModelProviderProfiles` with providers from `lib/agent/providers.ts`.
2. The client stores active provider and per-provider selected model under:
   - `agenticos.activeProvider`
   - `agenticos.providerModels`
   - `agenticos.providerThinking`
   - `agenticos.providerEffort`
3. `ModelProviderProfiles` calls:
   - `POST /api/model-providers/[provider]/test`
   - `GET /api/model-providers/[provider]/models`
4. Test/model routes use provider definitions and CLI availability helpers from `lib/agent/cli.ts`.
5. `PromptConsole` reads the stored values and passes `modelProfile` to `/api/runs`.
6. `lib/agent/llm.ts` dispatches generation by provider id/provider type:
   - CLI: Claude Code, Codex, GitHub Copilot CLI, Gemini CLI via `lib/agent/cli.ts`
   - Local: Ollama REST API
   - Cloud: NVIDIA, Anthropic, OpenAI, OpenRouter, Gemini, Grok
7. `computeCost()` in `lib/billing/pricing.ts` estimates cost based on configured pricing.

Change impact:

- Adding a provider requires changes in `types/agent.ts`, `lib/agent/providers.ts`, `lib/agent/llm.ts`, usually settings UI labels, test route, models route, and pricing.
- Changing localStorage keys breaks provider persistence in `PromptConsole` and `ModelProviderProfiles`.
- Changing CLI arg behavior in `lib/agent/cli.ts` affects both model runs and provider tests.
- Changing model names in `providers.ts` may affect pricing lookup and user-selected stored models.

### 4. Project Intelligence Injection

1. `.agenticos-project/` holds portable project instructions for all providers.
2. `lib/agent/project-context.ts` recursively loads markdown files, prioritizing root project docs, rules, agents, skills, commands, output styles, providers, hooks, and README.
3. Each file is capped at 3,500 chars and total context is capped at 18,000 chars.
4. `generateFinalOutput()` loads this context and passes it into model generation.
5. `systemPrompt()` and CLI prompt builders include the rendered context before task instructions.

Change impact:

- Changing `.agenticos-project` files affects all model providers and generated outputs without changing source code.
- Changing caps or priority in `project-context.ts` changes what the model sees and can alter behavior across all skills.

### 5. Vault and Memory Flow

The vault is the local markdown store and the app's durable memory.

1. `ensureVault()` creates folders: `raw`, `wiki`, `projects`, `content`, `daily`, `runs`, `drafts`, `memory`, `config`, `attachments`.
2. It also initializes Obsidian config under `vault/.obsidian`.
3. `writeVaultMarkdown()` writes frontmatter, markdown body, and related wiki links.
4. `createDailyNote()` is a daily-note wrapper around `writeVaultMarkdown()`.
5. `indexGeneratedArtifact()` writes memory metadata to `memory_index`.
6. `/vault` reads file lists, recent files, memory index, graph stats, backlinks/outlinks, promotion candidates, and conflicts.
7. `/api/vault` supports listing files and creating notes.
8. `/api/vault/graph` indexes wiki links and serves graph stats.
9. `/api/vault/autotag` patches note frontmatter with heuristic tags.
10. `/api/vault/conflict` detects duplicate titles, broken links, and dead references.
11. `/api/vault/patterns` scans daily notes for recurring terms.
12. `/api/vault/promote` moves highly-linked `raw/` notes to `wiki/`.

Change impact:

- `resolveVaultPath()` is the path traversal guard. Weakening it can allow writes outside the vault.
- `writeVaultMarkdown()` affects every run artifact, manual note, and daily note.
- `extractWikiLinks()` affects graph indexing and backlinks.
- `batchUpsertVaultGraph()` affects graph stats, promotions, backlinks, conflicts, and vault UI.
- `promoteNote()` physically copies and deletes notes; edit carefully and preserve `raw/` checks.
- Autotag route writes directly to note files; changes can rewrite user notes.

### 6. Database Initialization and Persistence

`lib/db/client.ts` owns SQL.js initialization and database schema creation.

Tables:

- `runs`: run metadata, status, token/cost estimates, plan JSON, files, errors, final output, artifacts.
- `run_steps`: step logs per run.
- `tool_calls`: planned/executed/blocked tool call ledger.
- `approvals`: approval requests and resolution state.
- `memory_index`: indexed vault artifacts and summaries.
- `integrations`: seeded integration metadata.
- `routines`: seeded routine schedules.
- `audit_logs`: historical audit events.
- `vault_nodes`: indexed notes with graph metrics.
- `vault_links`: wiki-link edges between vault notes.

Repository layer:

- `lib/db/repositories.ts` maps SQL rows into domain types, persists writes, and applies runtime integration state from env vars.
- Most pages and API routes never touch SQL directly. They call repository functions.
- SQL.js persistence requires calling `saveDb()` after mutation.

Change impact:

- Adding a DB column requires schema changes, insert/update changes, row parsing changes, and type changes.
- Failing to call `saveDb()` after writes loses data on process exit.
- `listRuns()` joins steps, tool calls, and approvals. Changing its shape affects dashboard, runs page, run detail page, metrics, command center, and API output.
- `listIntegrations()` overlays env-based real/connected status. UI status can change without DB rows changing.

### 7. Approval and Risk Flow

1. `lib/permissions/policy.ts` ranks risk levels and maps permission levels to approval requirements.
2. `detectRisk()` uses keyword heuristics.
3. `buildPlan()` in `engine.ts` combines skill risk and execution mode into `requiresApproval`.
4. During workflow execution, if a step requires approval and `dryRun` is false, a tool call is marked `blocked`, an approval row is inserted, and run status becomes `waiting_for_approval`.
5. `/approvals` lists approvals.
6. `components/approvals/approval-actions.tsx` patches approval status through `/api/approvals`.

Current limitation:

- Approving an approval only updates the approval row. There is no continuation executor that resumes the blocked tool call after approval.

Change impact:

- Changing risk terms or `requiresApproval()` affects whether workflows block, and therefore whether external actions are gated.
- Changing approval statuses requires type, DB, API, UI, and repository updates.

### 8. Scheduler and Routine Flow

1. Seed routines live in `data/seed-routines.ts`.
2. `lib/db/client.ts` inserts routine seeds when the DB is empty.
3. `/routines` displays routine overview from `lib/scheduler/routines.ts`.
4. `RoutineActions` toggles enabled state or runs a routine now through `/api/routines`.
5. `lib/scheduler/worker.ts` converts natural schedule strings into cron expressions.
6. On cron fire, it calls `createAndRunWorkflow()` with the routine skill and dry-run flag based on approval mode.
7. It touches `last_run` and logs audit events.

Change impact:

- Changing `naturalToCron()` changes which seeded and user routines actually schedule.
- Changing routine `approvalMode` changes whether scheduled workflows can block for approval.
- `createAndRunWorkflow()` is blocking, so long model calls in scheduled routines can occupy the scheduler task.

### 9. Command Center Flow

1. `/command-center` loads `getCommandCenterData()` from `lib/command-center/data.ts`.
2. That function concurrently reads runs, routines, local tasks, YouTube, Instagram, TikTok, Hacker News, and GitHub Trending.
3. It derives token burn, social tiles, latest upload, schedule slots, tasks, trending repos, HN stories, and weekly review.
4. `components/command-center/*` render the operational dashboard.
5. `TaskPanel` reads and mutates `vault/ops/tasks.md` through `/api/command-center/tasks`.
6. `TerminalPane` manages live CLI sessions through terminal API routes.

Change impact:

- Changing `CommandCenterData` shape requires updates in `app/command-center/page.tsx` and component props.
- Changing integration fetchers affects command-center live state and fallback behavior.
- `readTasks()` and `toggleTask()` write to `vault/ops/tasks.md`; changing task markdown format affects parsing.

### 10. Browser Terminal Flow

1. `components/command-center/terminal-pane.tsx` lazy-loads xterm.js in the browser.
2. It loads adapter availability from `GET /api/terminal/sessions`.
3. It starts a session with `POST /api/terminal/sessions`.
4. `lib/terminal/manager.ts` creates a PTY using adapter definitions from `lib/terminal/adapters.ts`.
5. Session cwd is `agenticosConfig.vaultPath`, not repo root.
6. Output is stored in memory, base64-encoded in `GET /api/terminal/[sessionId]/stream`, and written to xterm.
7. Keystrokes are sent to `POST /api/terminal/[sessionId]/input`.
8. Sessions can be killed with `DELETE /api/terminal/[sessionId]`.

Change impact:

- Changing session cwd changes what CLIs can see by default.
- Changing SSE encoding requires matching changes in `TerminalPane`.
- `sessions` is an in-memory Map; sessions disappear on server restart.
- Windows spawning behavior in `manager.ts` is deliberate because many CLIs resolve to `.cmd` shims.

### 11. Integration and External Data Flow

Current real read integrations:

- YouTube: channel stats, latest upload, recent videos.
- Instagram: follower, follows, media count.
- TikTok: profile stats.
- Hacker News: top stories.
- GitHub Trending: scraped trending page.

Mock adapter layer:

- `lib/integrations/adapters.ts` currently returns mock adapters for seeded integrations.
- Seeded integration metadata lives in `data/seed-integrations.ts`.
- Runtime status overlays in `listIntegrations()` mark integrations real/connected when env vars exist.

Change impact:

- Adding a real adapter means updating seed metadata, adapter implementation, permission policy, UI status, and tool-call logging.
- External write adapters must route through approval policy and audit logs.

### 12. MCP Flow

1. `/api/mcp` accepts server config `{ id, command, args, env }`.
2. `lib/mcp/bridge.ts` spawns the server process and speaks JSON-RPC over stdio.
3. `connectMcpServer()` sends `initialize`.
4. `listMcpTools()` calls `tools/list`, maps descriptions, and classifies risk.
5. `callMcpTool()` exists but is not currently exposed by the API route.
6. `disconnectMcp()` kills the process.

Change impact:

- MCP sessions are in-memory and die on restart.
- Any future tool-call route must use risk classification, approvals, and audit logging before calling mutating tools.

## Dependency Hotspots

### `lib/agent/engine.ts`

Depends on:

- Skills: `getSkill()`, `classifyPrompt()`.
- Models: `generateWithModel()`, `getProvider()`, `runSwarm()`.
- Context: `loadProjectModelContext()`, `loadVaultContext()`.
- Risk: `detectRisk()`, `requiresApproval()`.
- Persistence: run/step/tool/approval/audit/memory repository functions.
- Vault: `writeVaultMarkdown()`.
- Pricing: `computeCost()`.

## Safe Modification Playbooks

### Add a Skill

1. Add seed in `data/seed-skills.ts`.
2. Choose existing category from `types/skill.ts` unless a new category is truly needed.
3. Set correct `risk`, `mode`, `integrations`, and `output`.
4. If any routine should use it, update `data/seed-routines.ts`.
5. If category is new, update `categoryOutput`, `describe()`, `classifyPrompt()`, UI filters if present, and all category displays.
6. Run typecheck.

### Add an Integration

1. Add metadata in `data/seed-integrations.ts`.
2. Add env overlay in `applyRuntimeIntegrationState()` if it can become real.
3. Add live adapter/fetcher in `lib/integrations/`.
4. Wire it into UI/data layer that needs it.
5. Route writes through `lib/permissions/policy.ts`, approval rows, and audit logs.

### Add a Model Provider

1. Add provider type in `types/agent.ts`.
2. Add provider definition in `lib/agent/providers.ts`.
3. Add generation dispatch in `lib/agent/llm.ts`.
4. Add connectivity test in `app/api/model-providers/[provider]/test/route.ts`.
5. Add dynamic model listing in `app/api/model-providers/[provider]/models/route.ts` if supported.
6. Add UI label/support flags in `ModelProviderProfiles`.
7. Add pricing in `lib/billing/pricing.ts`.
8. Run typecheck.

### Add or Change a DB Field

1. Update table DDL in `lib/db/client.ts`.
2. Update insert/update SQL in `lib/db/repositories.ts`.
3. Update row type(s), parse mapping, and domain type(s).
4. Update UI/API consumers.
5. Consider migration behavior for existing `.agenticos/agenticos.sqlite`; `CREATE TABLE IF NOT EXISTS` does not alter existing tables.

### Add a Vault Feature

1. Use `resolveVaultPath()` for every user-provided path.
2. Keep all writes inside `agenticosConfig.vaultPath`.
3. Update API route, UI component, and repository graph/memory code only as needed.
4. Reindex graph if file paths or wiki links move.

### Add a Terminal Adapter

1. Add adapter in `lib/terminal/adapters.ts`.
2. Include `envVar`, aliases, args, and install hint.
3. Verify `createSession()` can start it through `lib/terminal/manager.ts`.
4. Make sure Windows command shim behavior still works.

## Known Limitations and Cautions

- There is no test suite in the current project. Use `npm run typecheck`, `npm run lint`, and `npm run build` as baseline checks.
- SQL migrations are not robust. Existing local DBs may not receive new columns unless migration logic is added.
- Many external integrations are read-only or mock-first.
- Approval resolution does not resume blocked workflow execution.
- Terminal sessions and MCP sessions are in-memory.
- `app/layout.tsx` triggers scheduler and vault graph indexing at module load; keep side effects lightweight.
- Several UI strings currently contain mojibake artifacts from prior encoding issues. Avoid introducing more; prefer ASCII unless intentionally fixing encoding.
- `node_modules/`, `.next/`, `.agenticos/`, and `vault/` are runtime/generated and should not be used as source-of-truth application code.

## How to Reason About Change Impact

Before editing, identify which layer owns the behavior:

- UI-only display issue: component under `components/` or page under `app/`.
- API contract issue: matching route under `app/api/` plus client component using it.
- Run lifecycle issue: `lib/agent/engine.ts`, repositories, run routes, run pages.
- Model/provider issue: `lib/agent/providers.ts`, `llm.ts`, `cli.ts`, model-provider API routes, settings UI, pricing.
- Vault issue: `lib/vault/*`, vault API routes, vault page/components, memory index.
- Persistence issue: `lib/db/client.ts`, `lib/db/repositories.ts`, shared types.
- Scheduler issue: `lib/scheduler/*`, routines API, routine page/actions.
- Terminal issue: `lib/terminal/*`, terminal API routes, `TerminalPane`.
- Command-center issue: `lib/command-center/*`, integration fetchers, command-center components.

Then check inbound consumers:

- Search for exported function name.
- Search for route path if changing an API.
- Search for localStorage key if changing settings/run provider state.
- Search for type name if changing a domain contract.
- Search for skill/integration/routine id if changing seed data.

## Final Mental Model

AgenticOS is not just a dashboard. It is a local workflow runtime:

- Skills define what the agent should do.
- Runs record every execution.
- The engine turns prompts into plans, tool-call ledgers, model output, vault artifacts, memory index rows, and audit logs.
- The vault stores durable markdown memory and artifacts.
- SQL.js stores operational metadata.
- Providers and CLIs generate text.
- Approvals and permission policy are the safety boundary.
- The command center reads many signals into one operational view.
- Scheduler turns routines into recurring dry-run or approval-gated workflows.

Most surgical edits are safe when they respect those boundaries.
